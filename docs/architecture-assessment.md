# 无后端 / 无数据库的可行性评估（量化版）

> 触发问题：方案 A 没有后端、没有数据库，**是否科学合理？是否需要调整优化？**
> 结论先行：**对阶段 1–2 是科学的**，但「无后端」不等于「无架构约束」——已经落地 4 项结构性调整（§5），否则未来接云端要重写存储与进度层。
> 依据：本仓库实测数据（2026-10-24）+ 环境审计结论。所有数字标注了测量方式或估算口径。

## 1. 结论

| 问题 | 回答 |
| --- | --- |
| 现阶段不要后端，合理吗？ | **合理**。当前是单人、离线优先、内容驱动、零并发冲突的产品，后端只会增加运维面与故障面 |
| 不要数据库，合理吗？ | **合理**。内容以文件为唯一事实源（可 diff、可评审）；学习记录是「单用户本地数据」，体积在 MB 级 |
| 需要调整吗？ | **需要**，但调整方向不是「加后端」，而是**加端口、加版本化、加同步友好的数据模型**（§5 已实现） |
| 什么时候必须加？ | 见 §7 的 6 个量化触发条件；其中「跨设备同步」和「在线 AI」是最可能先到的两个 |

## 2. 量化依据

### 2.1 内容体量（实测 + 外推）

| 项 | 实测 | 外推 |
| --- | --- | --- |
| 单个模块源文件（module.yaml + theory.mdx + tests.json + 示例代码） | **4,117 B**（实测 `content/co/cache-direct-mapped`） | — |
| 60 个模块（阶段 2 目标量级） | — | 源 ≈ **247 KB**；编译后 JSON（含题目与解析，约 2–3×）≈ **0.5–0.75 MB** |
| 单模块懒加载 chunk（gzip） | — | 估 **8–12 KB/模块** |
| 当前 Web 包（React + 应用，gzip） | **50.2 KB**（`vite build` 实测） | 首屏不受模块数量线性影响（动态 import） |

**判断**：内容量比一张照片还小。用静态 JSON + 懒加载就够了，**没有理由为一个 MB 级只读数据集引入数据库**。

### 2.2 用户数据体量（估算）

| 记录 | 单条约 | 数量假设 | 合计 |
| --- | --- | --- | --- |
| 学习进度 `ProgressRecord` | ~110 B | 60 模块 | ~7 KB |
| 答题记录 `AttemptRecord` | ~120 B | 60 模块 × 200 次 | ~1.4 MB |
| 导出备份（JSON） | — | 上述全部 | **< 2 MB** |

对比 IndexedDB 配额（Chromium 系约为可用磁盘的 60%，本机 D 盘 150 GB → 约 90 GB）：**余量 4 个数量级**。

### 2.3 并发与查询

- 并发：单人单浏览器；即使将来局域网 N≤5，也是各自本地库，无写冲突。
- 检索：60 模块全部文本 ≈ 360 KB，`MiniSearch` 内存索引约 1 MB，**单次查询 < 5 ms**；不需要全文数据库。
- 统计：跨用户统计（排行榜/考频）**确实需要服务端**——但这是产品后期才有的需求，且不阻塞教学闭环。

## 3. 分域判定（哪些功能真的需要后端）

| 功能域 | 需要后端？ | 理由 |
| --- | --- | --- |
| 知识内容、模块元数据 | **不需要** | 只读、可版本化、文件即事实源 |
| 模拟器与判题（客观题、手算） | **不需要** | 纯函数在浏览器算得又快又准；CI 用同一份代码验算 |
| 学习进度、收藏、错题 | **不需要**（但必须能导出） | 单用户本地数据；风险是「清缓存丢数据」→ 用导出/导入兜底 |
| 本地账号 | **不需要真实后端**，但**不是安全边界** | 口令在本机校验，可被绕过；仅用于同机多用户区分。**禁止当作公网身份** |
| 跨设备同步 | **需要** | 本阶段明确不做；数据模型已按 LWW 预埋（§5.2） |
| 在线 AI 讲题 | **需要**（BFF） | 模型密钥绝不能进浏览器；且要计费与限流 |
| 排行榜 / 考频统计 / 内容审核 | **需要** | 涉及跨用户聚合 |
| 用户私有题库导入 | **不需要**（本地） | 但若将来要分享，才需要服务端与审核 |

## 4. 无后端的真实代价（不粉饰）

| 代价 | 影响 | 现状缓解 |
| --- | --- | --- |
| 清缓存/换浏览器 → 进度丢失 | 中 | `StoragePort.exportAll()` + 导入（已实现并测试）；首次使用需提示导出 |
| 无法跨设备 | 中 | 明确写入产品边界；导出文件即「手动同步」 |
| 本地身份可绕过 | 低（当前场景） | 文档标注为「本机隔离」而非安全认证；公网前必须换真实认证 |
| 无法防作弊 | 低 | 教学产品不承诺防作弊；手算题允许「看解析」 |
| SEO / 分享卡片弱 | 中 | 阶段 2 用预渲染（`vite-plugin-ssg` 或构建期 HTML 快照）补 |
| 无服务端日志与监控 | 低 | 本地错误边界 + 用户可导出的诊断信息 |

## 5. 已落地的 4 项结构性调整（这才是「为扩展而设计」的部分）

### 5.1 存储端口化（Port & Adapter）

`packages/storage` 定义 `StoragePort`，当前两个适配器：

| 适配器 | 用途 |
| --- | --- |
| `MemoryStorage` | 单元测试、SSR 兜底 |
| `IndexedDbStorage` | 浏览器持久化（真实 IndexedDB，非内存模拟） |

未来只需要加一个 `HttpStorage implements StoragePort`，**UI 与模拟核心零改动**。

### 5.2 同步友好的记录模型

`ProgressRecord` 带 `revision` + `updatedAt`，合并用 **LWW（last-write-wins）**：

```ts
mergeProgress(local, incoming)  // revision 大者胜；相同则 updatedAt 新者胜
```

这一条现在几乎零成本，但决定了「将来能不能平滑同步」。**如果一开始用整表覆盖，接云端时必须重写**。

### 5.3 IndexedDB 版本化迁移钩子

`DB_VERSION = 1` + `upgrade(db, oldVersion)` 里的 `if (oldVersion < 1)` 分支模板，要求**只增不删**。
避免「以后加字段 → 用户本地库炸掉 → 只能让用户清数据」的常见事故。

### 5.4 内容与代码解耦 + 版权门禁

- `content/` 是唯一事实源，构建期由 `scripts/validate-content.mjs` 校验。
- 非原创内容必须 `authorized: true`，否则 **CI 直接失败**（已实现，当前 1 个模块通过）。

## 6. 模块化落地（回应「低耦合高内聚」）

```
protocol.ts   契约（无依赖）
   ↑
modules/<id>/ 每个模块一个文件夹：types + sim + 默认输入，只依赖 protocol
   ↑
registry.ts   显式注册表（懒加载），UI 不认识具体模块
   ↑
apps/web      渲染 + 播放器，不认识模拟器实现
```

**新增一个模块的改动面**（可验证的低耦合标准）：

1. `packages/sim-core/src/modules/<id>/{types,sim,index}.ts`
2. 注册表加 1 行
3. `content/<subject>/<id>/` 内容 + `tests.json`
4. 该模块的黄金测试
5. **不改动**：其它模块、播放器、存储层、UI 框架

跨模块组合（如 `cross.va-access-chain`）通过**组合 simulate 的产物**实现，而不是复制逻辑——这正是综合实验室能扩展的前提。

## 7. 迁移触发条件（量化，避免拍脑袋）

出现以下**任一**条件，就启动 `apps/api`：

| # | 条件 | 触发后要做的 |
| --- | --- | --- |
| T1 | 用户同时在 **≥2 台设备**上学习（每周都在用） | 真实账号 + 同步接口（复用 LWW） |
| T2 | 要上线 **在线 AI**（任何形式） | BFF 代理 + 密钥托管 + 计费 |
| T3 | 模块数 **> 200** 或内容 JSON **> 20 MB** | 内容服务化 / CDN 分片 |
| T4 | 需要**跨用户**统计、排行榜、题目质量分析 | PostgreSQL + 埋点 |
| T5 | 内容需要**按账号授权**（付费题库 / 私有导入分享） | 鉴权 + 内容分发 |
| T6 | 需要对**不可信用户**判题（防篡改） | 服务端复算（可直接复用 sim-core） |

## 8. 切换成本估算

| 层 | 是否需要重写 | 说明 |
| --- | --- | --- |
| `packages/sim-core` | **0 行** | 纯函数，浏览器/Node 同构 |
| `content/` | **0 行** | 文件即事实源，可原样导入 DB |
| `packages/storage` | 新增 1 个适配器 | 接口不变 |
| `apps/web` | 仅「选哪个适配器」的 1 处改动 | UI 不感知存储 |
| 新增 `apps/api` | 全新 | FastAPI 或 Node，接口照 `StoragePort` 设计 |

## 9. 成本对照

| 方案 | 现在 | 出现 T1/T2 后 |
| --- | --- | --- |
| 纯静态 | **¥0**（Cloudflare Pages / GitHub Pages 免费档） | — |
| 静态 + 轻 BFF | — | 最低约 ¥30–60/月（VPS）+ 对象存储/DB 免费档 |
| 全栈（方案 B） | 现在就要付运维与学习成本 | 与上者同量级，但提前背了复杂度 |

## 10. 因此，本次没有做的事（有意为之）

- 没有引入 Dexie / TanStack Query / 状态管理库：当前规模用原生 IndexedDB + React state 足够，**依赖越少，单人维护越稳**。
- 没有做「全站预渲染」：等模块数过 10 再上，避免过早优化。
- 没有写「云端账号」的假接口：契约已经在 `StoragePort`，不需要提前写空实现。
